# Redis 记忆 vs 内存记忆：8 维度对比（E1 实测版）

> 来源：E1 演进（2026-09-10）实测整理。所有结论锚定在 travel-agent 的真实代码与验证数据上，
> 面试可直接引用。配套代码：`memory/RedisChatMemory.java`、`service/RedisItineraryStore.java`。

---

## 一、8 个维度的区别

### 1. 生命周期（最本质的区别）
| | 内存 | Redis |
|---|---|---|
| 记忆归属 | 进程的堆里 | 进程外的独立存储 |
| 重启 | **全丢**——M4 时代每次重启服务，会话清零，必须重新生成攻略 | **存活**——E1 实测：重启后同 cid 直接 `/plan/adjust` 成功，记忆条数 4→6 正确累加 |
| 部署更新 | 发版=集体失忆 | 发版无感，用户会话不受影响 |

### 2. 多实例/水平扩展（换 Redis 的根本动机）
```
内存版：实例A ←→ 用户 ←→ 实例B        各存各的
        负载均衡把"第二轮调整"打到 B → B 没记忆 → 失忆
        更糟：A、B 都写了不同内容 → 数据分叉 = 串话

Redis版：实例A ─┐
        实例B ─┼→ Redis（唯一真相源）   任何实例服务任何会话
        实例C ─┘
```
一句话：**内存记忆把用户绑死在单实例上；Redis 记忆让"哪个实例接请求"变得无所谓**——这是负载均衡的前提条件。

### 3. 可观测性（本项目真实受益的点）
- 内存：黑盒。只能靠代码里 `memorySize()` 打个数字，看不到内容
- Redis：`redis-cli` 直接看真实数据——**E1 靠这个发现了内存时代的隐藏 bug**（`/plan/struct` 漏传 CONVERSATION_ID，消息一直落 "default" 桶，内存版完全不可见）

> 状态可见本身就是可观测性。

### 4. 过期与会话管理
- 内存：没有过期概念，只能靠窗口数量（20 条）被动挤掉旧消息；进程不重启、会话对象就一直在堆里
- Redis：**TTL 是一等公民**——本项目用滑动 TTL 24h（每次有新消息就续命），不活跃会话自动清理，天然匹配"会话"生命周期

### 5. 性能
- 内存：对象引用访问，纳秒级、零网络
- Redis：每次读写一次网络往返（本机 ~1ms 级）——本场景每请求 get 一次 + add 一两次，完全无感；QPS 上去可以 pipeline 批量

### 6. 故障模式（复杂度来源）
- 内存：不会"连不上"，但进程重启即**全损**
- Redis：多了一个外部依赖，会连接失败——所以做了**影子副本降级**：双写内存，Redis 挂了读影子。代价要诚实讲：降级后单实例可用，**跨实例共享和重启存活能力丢失**（可用性换一致性）

### 7. 序列化成本
- 内存：直接持有 `Message` 对象，零序列化
- Redis：必须序列化。本项目选了 **role+text 精简版**（tool calls/metadata 不落库）——够用，但这是明确的取舍；完整序列化 Message 多态体系要复杂得多

### 8. 数据结构自由度
- 内存：`MessageWindowChatMemory` 窗口逻辑是现成的
- Redis：**结构自己设计，跟着访问模式走**——记忆要"有序+滑窗"用 List+LTRIM；行程要"整树读写"用 String JSON

---

## 二、总结表

| 维度 | 内存 | Redis | 权重 |
|---|---|---|---|
| 重启存活 | ❌ 全丢 | ✅ 存活（实测） | 高 |
| 多实例共享 | ❌ 串话/失忆 | ✅ 唯一真相源 | 高（生产必须） |
| 可观测 | ❌ 黑盒 | ✅ cli 直接看（抓过 bug） | 中 |
| 会话过期 | ❌ 无 | ✅ 滑动 TTL | 中 |
| 性能 | 纳秒 | ~1ms/次 | 低（本场景无感） |
| 故障面 | 进程重启才丢 | 多一个依赖，需降级设计 | 中 |
| 复杂度 | 零依赖 | 部署+降级+序列化 | 低（值得付） |

**选择原则一句话**：单实例 demo/开发 → 内存（零成本）；要多实例/重启存活/会话生命周期管理 → Redis。不是"Redis 更好"，是**需求变了**。

## 三、面试金句（Day9 句式）

> "内存版我实测过它的两个硬伤：重启全丢、多实例串话。换 Redis 后跨重启连续性实测通过——重启后同 cid 直接调整，行程还是最新版本。但我没有无脑换：做了影子副本降级（Redis 挂了双写内存保单实例可用），并且明确降级的代价是丢跨实例能力。**外置存储还送了个意外红利：一个内存时代不可见的会话 ID 落桶 bug，redis-cli 一眼看到了。**"

## 四、E1 关键实现速查

| 组件 | 要点 |
|---|---|
| RedisChatMemory | List 结构；RPUSH 追加 + LTRIM 滑窗 20 条 + 滑动 TTL 24h；role+text 序列化；影子副本降级 |
| RedisItineraryStore | String JSON 整存整取；TTL 对齐 24h；同款降级 |
| 踩坑 | Spring AI 1.0.0 `ChatMemory.get` 是单参数签名 `get(String)`（不是文档示例的 `get(cid, lastN)`） |
| 踩坑 | Advisor 不传 CONVERSATION_ID 会落 "default" 桶——所有入口都要显式传 cid |
