## 〇、30 秒项目介绍（背熟）

> "我独立开发了一个旅行攻略智能体，Spring AI + DeepSeek 技术栈。用户输入目的地、天数、预算、偏好，Agent 会自主调用工具——查真实天气、检索我自建的城市知识库（RAG）、换算汇率——生成带逐日天气的结构化行程，支持多轮自然语言调整（'第二天太赶了'就只改第二天），最后可导出 Markdown。项目四层架构：对话层、工具层、知识层、工程层，全部能力实测验证过。开发中踩了不少真坑——比如模型输出不可信的问题，我做了三道防御。"

## 一、模型输出不可信的三道防御（最硬的故事，优先讲）

**背景**：/plan/struct 和 /plan/adjust 用结构化输出让模型返回 Itinerary JSON record 树。

**现象**（两个，先后爆发）：
1. 接口间歇性 500。日志：`Could not parse the given text: "Based on the request, the user wants to remove 明治神宫..."` ——模型在 JSON **前面先输出了一段思考**。
2. 用户反馈调整行程后"预计花费全变 0、没改的天也标了已调整"。

**排查**：
- 问题 1：`.entity()` 假设模型输出第一个字符就是 `{`。工具调用 + 结构化输出组合下，DeepSeek 偶尔不守规矩。复现不稳定（同 prompt 时好时坏）→ 系统性风险而非偶发 bug。
- 问题 2：注入 prompt 的"当前行程"用手写 toJson 拼接，**漏了 estimatedCost/mealSuggestion/tips 字段**——模型看不到旧费用，输出时全填默认值 0。前端 diff 比较 `JSON.stringify` 全对象，cost 550→0 也算"变了"，把没改的天误标"已调整"。

**修复**（三道防御，各挡一层）：
1. **格式防御**：BeanOutputConverter.getFormat() 生成 schema 注入 prompt（保持引导）+ `extractJson()` 截取首个 `{` 到末个 `}`（剥思考文字/围栏）
2. **快照防御**：给模型的行程快照改 Jackson 全量序列化——字段完整模型才不编
3. **字段防御**：`backfillMissing()` 对比新旧行程，模型抹零的字段从旧值回填（record 不可变 → 流式重建）

**教训**（金句）：
> "框架便利 API 背后是脆弱假设（模型永远规矩输出）。我把模型当不可靠的外部系统对待，在输出边界做防御——而且防御要分层：格式层、快照层、字段层，各挡各的。"
>
> "给模型的状态快照必须完整，缺什么它编什么。"

## 二、RAG 跨城市污染（讲 metadata filter 的最佳素材）

**背景**：6 城市 Markdown 知识库 → 切块 → bge-m3 → SimpleVectorStore，searchAttractions 工具内做 similaritySearch。

**现象**：成都攻略测试，日志显示 `检索命中 4 块，来源：成都、北京` ——topK 全库检索把北京的块混进来了（北京块的"美食"章节和查询语义相近）。

**修复**：建库时城市名写进 metadata（tokyo.md → "东京"），检索时：
```java
.filterExpression("city == '" + destination + "'")
```
修复后 `命中 2 块，来源：杭州` 纯净。

**放大**（主动讲）：
> "这和知识库权限隔离是同一机制——Document 带 metadata（部门/密级/城市），检索时按 filter 过滤。标签在建库时打，过滤在检索时做。我项目里是城市隔离，放大到企业场景就是数据权限。"

## 三、对话记忆 ≠ 业务状态（M4 核心设计）

**问题**：多轮调整（"第二天太赶了"）需要模型知道两件事——聊过什么（上下文）+ 当前行程长什么样（数据）。

**设计**：双状态分离
```
ChatMemory（MessageWindowChatMemory 窗口 20 条）→ 管"说过什么"（过程，可滑窗丢弃）
Map<cid, Itinerary>                              → 管"最新攻略"（结果，结构化持有）
```

**为什么不从聊天记录里拼行程**：又慢又不可靠。直接注入当前行程 JSON（Jackson 全量），模型只需输出修改后的完整行程，未提及的天保持原样。

**实测**：成都 3 日，第一轮"第二天太赶换茶馆"只动 Day2；第二轮"草堂换博物馆"只动 Day3——且 Day2 保持的是**第一轮调整后的版本**，证明状态正确迭代。调整一轮 3~9s（全量重生成要 20s+）。

**放大（已实施）**：
> "我后来真的把这套存储换成了 Redis（E1 演进）：自研 RedisChatMemory——Spring AI 没有官方 Redis 实现，我用 List 结构 + LTRIM 滑窗 20 条 + 滑动 TTL 24h 实现，行程状态用 String JSON 整存整取。降级做了影子副本：Redis 故障时双写降级为实例内存，单实例可用但跨实例共享能力丢失——降级不是免费的。**实测跨重启连续性**：重启服务后同 cid 直接调整成功，行程是重启前的最新版本、记忆条数正确累加。还有个意外收获：外置存储让一个内存时代的隐藏 bug 现形（漏传 conversationId 落到 default 桶）——状态可见本身就是可观测性。"

## 四、降级策略分数据类型（天气 API 的哲学）

**决策链**：wttr.in 免费无 key → 但只认英文城市名（中文实测 location not found）→ 24 城中英映射表。

**关键取舍**：初版做了"API 失败 → Mock 假数据"兜底，后来**主动删掉**了：
> "天气是实时观测值。用户在暴雨天拿到'晴 22°C'的假数据，比'暂时查不到'危害大——假数据会误导行程决策。降级要分数据类型：**静态参考值可以缓存兜底（标注时效），实时观测宁可缺失**。失败路径走否判断：告诉模型查不到，让它转常识建议并提醒用户出发前自查。"

**加分细节**：逐日预报（3 天温度/降雨概率/UV）写进 DayPlan.weather 后，实测模型行为改变——Day2 降雨 77%，主动把全天户外改成"灵隐禅意+短途徒步，雨大转茶叶博物馆"。**天气数据真正参与了行程决策**。

## 五、Agentic RAG vs 固定管道

**对比**（能画图讲）：
```
固定管道：用户问题 → 必检索 → 拼上下文 → 生成（代码写死，查什么都定好）
Agentic ：检索是 @Tool → 模型自主决定 查不查/查什么关键词/查几轮/怎么组合
```

**实测证据**：杭州 3 日请求，模型自主编排 5 连调：`getCurrentDate → getWeather → getTravelTips → searchAttractions(美食) → searchAttractions(地标)`——顺序和主题都是模型定的，代码里零编排逻辑。伊斯坦布尔（知识库外）模型收到否判断后自主降级常识推荐+标注未核实+自己找 USD 替代 TRY 换算。

**踩坑经验**（检索参数）：
> "相似度阈值我设 0.0 靠 topK 截断——bge-m3 中文召回好但旅游口语化查询相似度分数天然偏低，卡阈值容易全军覆没。这是我 embedding 选型时实测过的（nomic 中文翻车，弃用换 bge-m3）。"

## 六、架构与演进（谈规划必背）

**四层架构**（30 秒讲完）：对话层（ChatClient/记忆/流式）→ 工具层（5 @Tool ReAct）→ 知识层（Agentic RAG）→ 工程层（防御/降级/导出）。

**放大清单**（每个都能接"我这个项目里实测过 X，放大到企业级要换 Y"）：

| 现在（实测版） | 企业级 | 为什么 |
|---|---|---|
| ~~内存 ChatMemory + Map~~ → 已换 Redis（自研 ChatMemory，E1） | Redis 集群/哨兵 | 多实例共享，否则串话（已完成第一版） |

## 七、高频追问速答

**Q: 为什么选 DeepSeek 而不是 GPT/GLM？**
A: OpenAI 兼容协议（Spring AI 只需换 base-url）、中文效果好、价格低。架构上 ChatClient 与模型解耦，换模型只改配置——这正是 Spring AI "与模型无关 API"的价值，我实测过 deepseek-chat 和 deepseek-reasoner 单请求切换。

**Q: token/延迟数据？**
A: 我做了 Micrometer 打点（自定义 CostTrackingAdvisor：延迟/token/工具轮数/成本一行账单 + /actuator/prometheus），真实数字（deepseek-chat，杭州 2 日攻略）：**主生成 10.7s、输入 7148 + 输出 1768 token、6 轮工具调用、成本 ¥0.0284**；多轮调整约 ¥0.02/次。打点还立刻暴露了一个浪费：生成后补写一句初始上下文走了带全套工具的 client，模型为这句废话又调 4 轮工具烧 4161 token——占主生成成本 65%，优化方向是无工具轻量通道。**先打点再优化，凭感觉都是猜。**

**Q: 流式和结构化能同时要吗？**
A: 能但复杂（结构化需要完整 JSON 才能解析，流式片段拼 JSON 要增量解析器）。我的取舍是两种模式分开：流式给人看（Markdown），结构化给程序用（Itinerary 对象），共用同一个 buildPrompt 保证语义一致。

**Q: 最有成就感的坑？**
A: 结构化输出三防御（故事一）。因为它教我的是方法论：便利 API 的脆弱假设藏在哪、防御为什么要分层、以及"给模型的输入也要防御"这个反直觉认知——大家都防输出，没人防输入。

**Q: 打点/可观测讲一个具体的坑？**
A: 成本响应头第一次做时死活不出来：同样位置的 setHeader，ASCII 值出现、含中文的值凭空消失、零报错。定位靠二分实验（方法首行设测试 header → 出现 → 锁定值的问题）。根因：**Tomcat 对非 ASCII 的 header 值静默丢弃**——HTTP 头是 ISO-8859-1 字节流，中文想进 header 必须 ASCII 化或 RFC 5987。这类"静默失败"最危险，没有报错的 bug 只能靠对照实验定位。

**Q: 安全做过什么？**
A: 目前三个点：导出接口文件名清洗防目录穿越、cid 会话隔离、api-key 只走环境变量。规划中：PII 脱敏、限流。（诚实说规划，别吹已有）
